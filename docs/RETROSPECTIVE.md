# 回忆与总结经验 —— EVA 小游戏合集从第一天到现在

> 写于 v1.5.6 发版当晚。158 个提交、15 个玩法、11 套 202 项回归测试、
> 从 2026-09-05 一天成型的连连看，到 09-29 的分组大厅与图库选照。
> 这份文档既是回忆，也是把踩过的坑变成下次的路标。

---

## 一、起源：一天成型的连连看（09-05）

一切从 20:30 开始。当晚的目标很朴素：**给明日香和绫波丽做一个连连看**。

20:30 基础版跑通（safebooru 抓图筛 12 张牌面、8×6 棋盘、经典 2 拐点规则、保证可解发牌），
20:40 修掉第一个 bug（发牌数量只压了一半——每种图案应 2 对 4 张，结果棋盘只剩半盘有牌），
然后是停不下来的一晚：21:10 壁纸图库与轮换背景、21:40 EVA 侧边装饰栏（同步率面板随战况上涨）、
22:10 难度选择与战绩、22:40 牌面扩到 28 种、23:05 使徒级 8 局连续关卡、23:20 发布 GitHub。

**一天内，"一个连连看"变成了"一个有氛围的 EVA 小游戏"。**
事后看，真正定调的是三个决定：
1. **壁纸即背景**——图库照片轮换作全屏背景，游戏浮在上面。这个决定让所有后续玩法天然"出生即有氛围"；
2. **装饰栏同步率面板**——NERV 徽记、MAGI 三贤人、随战况上涨的同步率，成了整个合集的视觉签名；
3. **开局先选玩法**——从第二个玩法（五珠对弈）起，"玩法大厅"的骨架就立住了，后面每加一个玩法只是加一张卡片。

## 二、生长：从单游戏到合集（09-06 ~ 09-13）

之后的路径几乎是匀速生长：

- **桌面化**：vbs 启动器 → 无缓存本地服务（serve.py，修 Edge 缓存旧清单的坑）→ pywebview + PyInstaller 独立程序 → 单文件安装程序 → 在线更新机制；
- **玩法一个个长出来**：五珠对弈 → 观景·挂机 → 蜘蛛纸牌 → 使徒扫雷 → 数独 → 拼图 → 接龙 → 三消；
- **图库成为基础设施**：本地 API 支持上传/删除、缩略图自动生成、manifest 自动重建——后来拼图和记忆训练直接把图库当关卡库用。

这个阶段最值得回忆的是**蜘蛛纸牌的"微软规则长战役"**：从"自创规则跑不通"到逐条对齐微软语义，
前前后后十几个提交——放置与收套方向矛盾、叠放层序、列排布视觉、build-down 降序延伸、
段顶 +1 接列底明牌、单向 K 顶 A 底收套……最后以"规则测试 12/12 + 页面断言 15/15 + 真实点击链路"验收收尾。
它教会我们：**抄经典游戏，就要抄到语义级；规则测试是唯一的裁判**。

另一个有趣的插曲：牌面从 12 种扩到 28 种，是因为一句"重复度太高"——
**用户的实机感受永远比设计文档诚实**。

## 三、磨合：与实机反馈的循环（09-17 ~ 09-29）

v1.4.x 之后，开发节奏变成了"实现 → 实机 → 反馈 → 修复"的循环，
也让一批真问题浮出水面：

- **暴走永远无法触发**（v1.5.1 修复）：同步率增益被 clamp 在恰好 100，
  而每帧结算"先衰减再判定"——判定时恒为 99.995。这个 bug 跨两个游戏同源存在，
  直到写弹球时用"模拟玩家探针"发现"暴走次数恒为 0"才暴露。
  修复的同时给两个游戏都加了**模拟真实帧序的守护测试**（含一条"顺序写反则触发不了"的回归用例）。
- **EVA 突击的道路消失**：砖块离屏缓存用源矩形开窗，与外层 translate(-cam) 叠加成 2 倍位移——
  关卡中后段整层地面滑出画面。此前所有验证截图都在镜头位移为零的出生点拍摄，恰好测不出。
- **角色黑脸**：下颌影把 fillStyle 设成半透明黑，紧接着的脸部圆没有重设填充色。
- **塔防三档难度全打不通**：靠"模拟 AI 玩家跑完整局"的平衡探针校准了经济曲线。

这一阶段的结论浓缩成一句话：**纯函数测试全绿 ≠ 集成正确；视觉验证必须覆盖参数的非零场景。**

## 四、插曲与弯路（同样值得记录）

- **版本号的教训**：v1.5.2 时我因"新增两个玩法"自作主张定了 v1.6.0，被纠正回 v1.5.2——
  此后版本号只递增 patch 位（v1.5.9 之后才 v1.6.0），规则已入长期记忆。
- **ZCode 框架缺陷反馈**（issue #740）：提交后才知道用户早已通过应用内渠道反馈过——
  **查重不能只查公开渠道**，私下渠道不会留下检索痕迹。issue 已按用户要求关闭。
- **蜘蛛纸牌的多次返工**、**2048/记忆的镜像测试漂移风险**（后改为从页面标记块直接提取，杜绝双份维护）：
  每一次返工都在说同一件事——**约定要有机械校验，不能靠自觉**。

## 五、经验总结（按价值排序）

### 工程结构
1. **无构建、纯静态、单文件页面**是这个项目最重要的架构决定：每个玩法一个自包含 HTML，
   共享的只有三个 JS（背景/装饰/图库）和一个本地服务。15 个玩法零依赖、克隆即玩。
2. **约定优于配置**：页面骨架九段式、难度叫 見習い/正規隊員/使徒級、最高分键名
   `eva_<玩法>_best_<难度>`、开局先选玩法、`🎮 玩法选择` 回大厅——约定让第 15 个玩法的接入成本和第 2 个一样低。
3. **打包脚本通配根目录**：新玩法页放进根目录自动进包，构建清单只做"关键文件在位"保险。

### 测试策略
4. **纯逻辑抽成镜像块**（页面与 `*-test.js` 逐字一致），玩法规则才有回归可言；
   后期改为**从页面标记块直接提取**，消除双份维护。
5. **平衡性要用模拟探针跑完整局**：塔防三档全打不通、弹球垂直死循环，都是探针先于用户发现的。
6. **守护测试写"错误写法确实不行"**：暴走顺序缺陷的回归用例反过来断言"先衰减后判定触发不了"，
  把坑本身变成测试资产。

### 渲染与交互
7. **Canvas 是状态机**：fillStyle 不重置就是下一个绘制的颜色（黑脸 bug）；
   复杂单路径填充的绕行方向不可凭直觉（头发盖脸 bug），拆成简单形状最稳。
8. **变换叠加要算清楚**：drawImage 源矩形开窗 + 外层 translate 叠加 = 2 倍位移（道路消失）。
9. **视觉验证覆盖参数非零场景**：出生点截图测不出镜头位移 bug。
10. **性能问题的第一嫌疑人是每帧分配**：每帧 200 个渐变对象 → 离屏缓存后 0.12ms/帧。

### 流程
11. **实机反馈是最快的平衡性工具**：牌面重复度、塔防经济、弹球手感，全部来自"玩过再说"。
12. **发版流水线固化成脚本**（build_release.py + create_release.py + api_push_files.py），
    发版从"临场调 API"变成一条命令；版本号规则（patch 递增）写入长期记忆。
13. **跨会话状态用 SESSION-NOTES 承载**：目标/决定/状态/待办四段式快照，下次会话零上下文损失。
